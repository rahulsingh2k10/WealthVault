WealthVault API (1.0.0)

Download OpenAPI specification:

OAuth sign-in, vault-unlock, and profile routes for WealthVault, generated from user-creation-api.md and unlock-api.md.

Scope: this spec covers the four OAuth providers' initiate + callback routes, POST /api/auth/unlock, and PATCH /api/auth/avatar.

WealthVault has no dedicated "create a user" endpoint: a users row is created or updated as a side effect of a successful OAuth callback (a Prisma upsert), detailed below. There is also no generic "edit profile" endpoint — fullName and username are only ever refreshed via that same OAuth login upsert; avatar is the one user detail with its own dedicated update route (PATCH /api/auth/avatar).

What every OAuth callback writes to users (the upsert)

Column On create (new username) On update (returning user)
id auto-generated uuid() unchanged
fullName from the provider profile refreshed from the provider profile
username provider-derived identity string (email, or bare handle for X) — this is the upsert key unchanged
auth_platformId FK to auth_platforms.id, resolved from the provider refreshed
avatar provider's photo URL, or omitted entirely for Apple refreshed (Google/LinkedIn/X only — never for Apple)
subscriptionPlanId FK to subscription_plans.id, always the FREE row's id never touched — a returning user keeps whatever tier they're on
verifier left NULL (set later by POST /api/auth/unlock) untouched
createdAt / updatedAt set automatically by Prisma updatedAt refreshed

What a successful callback writes to the session cookie

Every callback seals a portfolio_session cookie (see the SessionCookie security scheme below) containing:

Field Value
userId the User.id of the row just created/updated
userName User.fullName
userEmail User.username
userAvatar provider avatar URL, or "" for Apple/X-without-image

subscription is deliberately not included in this cookie.

Failure redirect codes (/?error=<code>)

On any of these, no row is created or modified in users — the upsert is either never reached, or its result is discarded because the route already returned:

Code When
access_denied (or whatever code the provider sent) User declined consent on the provider's screen
missing_params Callback arrived without code or state
invalid_state CSRF check failed, or (X only) the PKCE x_code_verifier cookie was missing
token_exchange_failed The provider rejected the authorization code
invalid_user_info Provider's profile endpoint didn't return the required fields (Google/X/LinkedIn only — Apple has no equivalent check)
server_error Any unhandled exception, including a failed upsert

Apple is the one provider that calls its callback with POST + a form-encoded body instead of GET + a query string, per Apple's response_mode=form_post.

Profile fetch: decoded id_token JWT email claim (→ username, falls back to apple_{sub}@apple.com since Apple omits email on repeat logins) + the one-time user field (→ fullName, first login only).

Database effect on users (full table in the Info section above): auth_platformId set to the APPLE row's id, avatar never set (Apple exposes no profile picture).

Unlock

Vault passphrase setup/verification, run after OAuth sign-in

Verify a returning user's passphrase, or establish a first-time user's passphrase

There is exactly one route for both signup and login of the vault passphrase — it silently branches into a first-time (create) or returning (verify) path based on whether the signed-in user's verifier column is currently NULL. Requires an existing OAuth session (session.userId); this is the second of two distinct authentication steps (OAuth proves who you are, this proves you know the vault passphrase).

Authorizations:
SessionCookie
Request Body schema: application/json
required
passphrase
required
string

The vault passphrase, plaintext, sent once over HTTPS. Never persisted as plaintext anywhere — see the UnlockResult schema.

Profile

Updating an existing user's own details

Update the current user's avatar

Overwrites users.avatar with a client-uploaded image and keeps the session's userAvatar in sync, replacing whatever avatar the OAuth provider originally supplied. Independent of the unlock flow — can be called before or after POST /api/auth/unlock.

Database effect: UPDATE users SET avatar = <data URL> WHERE id = :userId.

Session

Ending an existing session

End the current session

Destroys the portfolio_session cookie's contents — userId, userEmail, userAvatar, and (if the vault was unlocked) encryptionKey — in one call. No request body. Idempotent: calling this with no session, an expired session, or an already-cleared session all succeed identically; there's no session state to check beforehand, so this route never returns 401.

Dashboard

The protected page reached after OAuth sign-in and vault unlock

Load the dashboard page

A page route, not a JSON API — included here because access to it is gated by the same session cookie as the rest of the app, enforced by frontend/src/middleware.ts before this route's own handler ever runs.

The page component itself repeats the encryptionKey check (if (!session.encryptionKey) redirect('/unlock')), but in normal operation the middleware has already redirected away before that line can execute — it's a defensive second check, not the primary gate.

Currently renders the app shell (sidebar + header) with an intentionally blank content area — the portfolio-summary data wiring this page used to call (PortfolioService/AssetRepository) depended on Prisma models that don't exist in the current schema and has been removed; no request to this route can throw as a result of that missing wiring anymore.
