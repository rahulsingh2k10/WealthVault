# Database: `user_preference` Table

> Source of truth: `prisma/schema.prisma` (frontend). `backend/prisma/schema.prisma` is
> kept byte-identical for this model — the backend service has no logic of its own that
> touches `user_preference`, it just needs a matching schema against the same database so
> a backend migration never generates a drop for it.

## Overview

- **Prisma model name:** `UserPreference`
- **Table name:** `user_preference` (via `@@map("user_preference")`)
- **Database:** PostgreSQL, hosted on Railway (`DATABASE_URL` in `frontend/.env`)
- **Migration strategy:** no `prisma/migrations` history exists for this project — schema
  changes are applied directly with `prisma db push`.
- Zero-to-three rows per user — a key/value store of the three app-settings a user can
  change from the UI: their **country**, their **language/locale**, and their
  **theme** (dark/light). A row exists only once the user has explicitly set that
  preference at least once; until then the API serves a hard-coded default. There is
  never more than one row per `(userId, key)` pair.

This table replaces the earlier `app_config` table (Prisma model `AppConfig`), which was
dropped from the schema in commit `f589006` and left the preferences UI silently
non-functional until this table restored it.

## Column reference

| Column      | Type       | Nullable | Default  | Notes                                             |
|-------------|------------|----------|----------|---------------------------------------------------|
| `id`        | `String`   | No       | `uuid()` | Primary key                                       |
| `userId`    | `String`   | No       | —        | Foreign key to `users.id`                         |
| `key`       | `String`   | No       | —        | One of `country`, `locale`, `theme`               |
| `value`     | `String`   | No       | —        | The preference value (see **Value formats** below) |
| `createdAt` | `DateTime` | No       | `now()`  | Row creation timestamp                            |
| `updatedAt` | `DateTime` | No       | auto     | Auto-updated on every write (`@updatedAt`)        |

### Column details

- **`id`** — UUID, generated by Prisma. Not referenced as a foreign key from any other table.
- **`userId`** — See **Relationships** below.
- **`key`** — Free-form `String` at the database level; the application only ever writes
  one of `country`, `locale`, `theme`. The `PATCH /api/preferences` route rejects any
  other key with a `400` before it reaches the database (see `documents/api/preferences-api.md`).
- **`value`** — Free-form `String`. Not validated against an enum at the database level.
- **`createdAt`** — Set once, at row creation (first time the user sets that preference).
- **`updatedAt`** — Updated automatically by Prisma every time the user changes that
  preference (the route uses `upsert`, so subsequent changes are an `UPDATE` of the same
  row, not a new row).

### Value formats

| `key`     | `value` shape                              | Examples                       | Default when no row |
|-----------|--------------------------------------------|--------------------------------|---------------------|
| `country` | ISO 3166-1 alpha-2, uppercase              | `IN`, `US`                     | `US`                |
| `locale`  | IETF BCP 47 tag (one of `LOCALES` in `src/i18n/translations.ts`) | `en-US`, `hi-IN`, `de-DE` | `en-US`             |
| `theme`   | `dark` or `light`                          | `dark`                         | `dark`              |

The defaults live in `DEFAULTS` in `src/app/api/preferences/route.ts`, not in the
database.

### Full current model (for reference)

```prisma
model UserPreference {
  id        String   @id @default(uuid())
  userId    String
  user      User     @relation(fields: [userId], references: [id])
  key       String // "country" | "locale" | "theme"
  value     String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([userId, key])
  @@map("user_preference")
}
```

## Current data

Written exclusively by `PATCH /api/preferences`
(`src/app/api/preferences/route.ts`), via:

```typescript
await prisma.userPreference.upsert({
  where:  { userId_key: { userId: session.userId, key } },
  update: { value },
  create: { userId: session.userId, key, value },
})
```

The `PATCH` is fired from these places in the frontend, all of them user actions:

| Trigger | File |
|---|---|
| Country picker on the Settings page | `src/components/settings/SettingsPanel.tsx` (via `setCountry`) |
| Language picker on the Settings page | `src/components/settings/SettingsPanel.tsx` (via `setLocale`) |
| Dark/Light toggle on the Settings page | `src/components/settings/SettingsPanel.tsx` |
| Theme pill in `AppBar`, shown only on `/` and `/unlock` | `src/components/layout/ThemeTogglePill.tsx` — only writes successfully from `/unlock` (a session already exists there); on `/` the write 401s and is swallowed |

`/settings` is the only place Country and Language can be changed at all — the sidebar's
own Country/Language pickers and its theme pill were removed; theme can also still be
changed pre-unlock via the `AppBar` pill described above. On sign-out, the *applied*
theme reverts to the OS setting (`next-themes` `setTheme("system")`), but this table's
stored `theme` row is left untouched and is restored on the next sign-in — see
`docs/superpowers/specs/2026-09-09-signout-theme-reset-design.md`.

`setCountry` / `setLocale` (`src/context/LocaleContext.tsx`) and the theme toggles call
the shared helper `savePreference(key, value)` (`src/lib/savePreference.ts`), a
fire-and-forget `PATCH` — a failed write is swallowed and never surfaced to the user,
because a cookie / `localStorage` copy of each value is always kept as the immediate
source for rendering.

On load, `PreferencesSync` (`src/components/layout/PreferencesSync.tsx`, mounted once in
`src/app/layout.tsx`) calls `GET /api/preferences` and applies the returned values to the
locale context and `next-themes`, making the stored preferences the cross-device source
of truth.

No other route or code path reads or writes this table.

## Constraints & indexes

- **Primary key:** `id` (`uuid()`, generated by Prisma, not the database)
- **Unique constraint:** `(userId, key)` — the `@@unique([userId, key])` — enforces at
  most one row per user per preference key. It also backs the `userId_key` compound
  selector the `upsert` uses. Postgres names the index `user_preference_userId_key_key`.
- **Foreign key:** `userId` → `users.id` — see **Relationships** below.
- No other indexes are defined.

---

## Relationships

**`user_preference.userId` → `users.id`** (foreign key, constraint
`user_preference_userId_fkey`, `ON DELETE RESTRICT`, `ON UPDATE CASCADE` — Prisma's
implicit defaults for this relation): every preference row belongs to exactly one user.

- **Referential integrity is enforced by Postgres** — a `user_preference.userId` value
  must match an existing `users.id` row.
- **You cannot delete a `users` row while any `user_preference` row still references it**
  — `ON DELETE RESTRICT` blocks it. There is no cascade delete; application or test code
  that removes a user must delete its `user_preference` rows first (see
  `tests/helpers/testUser.ts`).
- **Updating a `users.id` cascades automatically** — `ON UPDATE CASCADE`.
- **The reverse relation** `User.userPreferences UserPreference[]` lets application code
  fetch a user's preferences with
  `prisma.user.findUnique({ where: { id }, include: { userPreferences: true } })`, though
  no code does this yet — the API route queries `user_preference` directly by `userId`.
