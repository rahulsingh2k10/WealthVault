# Database: `subscription_plans` Table

> Source of truth: `prisma/schema.prisma` (frontend). `backend/prisma/schema.prisma` is
> kept byte-identical for this model — the backend service has no logic of its own that
> touches `subscription_plans`, it just needs a matching schema against the same database.

## Overview

- **Prisma model name:** `SubscriptionPlan`
- **Table name:** `subscription_plans` (via `@@map("subscription_plans")`)
- **Database:** PostgreSQL, hosted on Railway (`DATABASE_URL` in `frontend/.env`)
- **Migration strategy:** no `prisma/migrations` history exists for this project — schema
  changes are applied directly with `prisma db push`.
- One row per `Tier` (`FREE`, `MONTHLY`, `QUARTERLY`, `ANNUAL`) — a global pricing
  reference table, not per-user data. Compare to `users`, which has one row per person;
  this table has a fixed, small number of rows (one per tier) that describe what each
  tier costs and, for paid tiers, which Razorpay Plan it bills against.

## Column reference

| Column           | Type        | Nullable | Default  | Notes                                                  |
|------------------|-------------|----------|----------|---------------------------------------------------------|
| `id`             | `String`    | No       | `uuid()` | Primary key                                            |
| `tier`           | `Tier`      | No       | —        | Unique tier identifier (FREE/MONTHLY/QUARTERLY/ANNUAL) |
| `price`          | `Decimal`   | No       | —        | List price for the tier, per billing cycle             |
| `offerPrice`     | `Decimal?`  | Yes      | —        | Discounted price when a promotion is active            |
| `currency`       | `String`    | No       | `"INR"`  | Currency code, e.g. `"INR"`                            |
| `offerStartDate` | `DateTime?` | Yes      | —        | Offer price start date                                 |
| `offerEndDate`   | `DateTime?` | Yes      | —        | Offer price end date                                   |
| `isActive`       | `Boolean`   | No       | `true`   | Hides a plan without deleting it                       |
| `createdAt`      | `DateTime`  | No       | `now()`  | Row creation timestamp                                 |
| `updatedAt`      | `DateTime`  | No       | auto     | Auto-updated on write                                  |
| `razorpayPlanId` | `String?`   | Yes      | —        | Razorpay Plan ID this tier bills against. `NULL` for `FREE`. |
| `intervalMonths` | `Int?`      | Yes      | —        | Billing interval, in **days** despite the name — see below |
| `termMonths`     | `Int?`      | Yes      | `36`     | Mandate term, in **days** despite the name — see below |

### Column details

- **`id`** — UUID, generated by Prisma.
- **`tier`** — `Tier` enum (`FREE`, `MONTHLY`, `QUARTERLY`, `ANNUAL`). The Prisma model is named `Tier`; the enum carries `@@map("Subscription")`, so the underlying Postgres enum type is still called `Subscription` — application code always imports/references it as `Tier`. Not a foreign key target — see **Relationships** below; `users.subscriptionPlanId` references `id`, not this column.
- **`price`** — `Decimal` (Postgres `numeric`) was chosen over `Float` specifically to avoid binary floating-point rounding error for money. No `@db.Decimal(p, s)` precision/scale is pinned, so Postgres defaults to unbounded precision. Stored as a **whole currency unit** (rupees for INR), not paise — `POST /api/subscription/create` multiplies `offerPrice ?? price` by `100` to get the paise amount Razorpay's API expects.
- **`offerPrice`** — `NULL` means no offer — the tier is sold at `price`.
- **`currency`** — ISO-ish currency code as free text (not a Prisma enum). The default is a placeholder based on the app's existing India-specific instruments (NPS, PPF, Post Office schemes); nothing stops a per-row override.
- **`offerStartDate`** — When `offerPrice` starts applying. `NULL` alongside a non-null `offerPrice` has no defined meaning — nothing in code reads or enforces this relationship (see **Data integrity caveats**).
- **`offerEndDate`** — When `offerPrice` stops applying and the tier reverts to `price`. Same caveat as above — schema-only, not wired to any logic.
- **`isActive`** — Hides a plan from a future pricing page without deleting its row (and without losing the `@unique` slot for that `tier`). Not read by any code yet.
- **`createdAt`** — Set once, at row creation.
- **`updatedAt`** — Updated automatically by Prisma on every write to the row (`@updatedAt`).
- **`razorpayPlanId`** — The Razorpay-side Plan ID this tier's checkout creates a subscription against (`POST /api/subscription/create` and `POST /api/subscription/change-plan` read it via `prisma.subscriptionPlan.findUniqueOrThrow({ where: { tier } })`). `NULL` for `FREE`, which never goes through Razorpay. Sourced from `RAZORPAY_PLAN_ID_MONTHLY`/`RAZORPAY_PLAN_ID_QUARTERLY`/`RAZORPAY_PLAN_ID_ANNUAL` env vars at seed time (`frontend/prisma/seed.ts`, `tests/helpers/seedReferenceData.ts`) — not looked up from the environment at request time.
- **`intervalMonths`** — Despite the column name, this is a **day count**, not a month count. Razorpay Plans in this project bill daily (e.g. every 7/9/12 days for MONTHLY/QUARTERLY/ANNUAL) rather than on a monthly cadence; the column was named before that changed and has not been renamed. `NULL` for `FREE`.
- **`termMonths`** — Same day-count caveat as `intervalMonths`: the 3-year mandate term is expressed as `1095` (365 × 3) days, not months. `NULL` for `FREE`; the schema default of `36` is a pre-Razorpay leftover and is overridden by every seed path for paid tiers.

### Full current model (for reference)

```prisma
enum Tier {
  FREE
  MONTHLY
  QUARTERLY
  ANNUAL

  @@map("Subscription")
}

model SubscriptionPlan {
  id                      String                    @id @default(uuid())
  tier                    Tier                      @unique
  price                   Decimal
  offerPrice              Decimal?
  currency                String                    @default("INR")
  offerStartDate          DateTime?
  offerEndDate            DateTime?
  isActive                Boolean                   @default(true)
  createdAt               DateTime                  @default(now())
  updatedAt               DateTime                  @updatedAt
  users                   User[]
  subscriptionPlanHistory SubscriptionPlanHistory[]
  razorpayPlanId          String?
  intervalMonths          Int?
  termMonths              Int?                      @default(36)
  subscriptions           Subscription[]

  @@map("subscription_plans")
}
```

## Current data

`FREE` is seeded with `price: 0` and no Razorpay wiring (`razorpayPlanId`/`intervalMonths`/
`termMonths` all `NULL`) — every new sign-up lands here, and it never goes through
checkout. `MONTHLY`/`QUARTERLY`/`ANNUAL` are seeded with a non-zero `price`, a discounted
`offerPrice`, and a `razorpayPlanId` sourced from the `RAZORPAY_PLAN_ID_MONTHLY`/
`RAZORPAY_PLAN_ID_QUARTERLY`/`RAZORPAY_PLAN_ID_ANNUAL` environment variables. Exact live
values (price/offerPrice/offer dates) should be read from the database rather than assumed
from any seed file, since a promotional `offerPrice` window is time-bound and expected to
change independently of any code or doc update.

**`frontend/prisma/seed-reference-data.ts`** (`npm run db:seed-reference`) is the script
that seeds this table: one `upsert` per `Tier`, keyed on `tier`, so it's safe to re-run
against a database that already has rows. It seeds `auth_platforms` the same way in the
same run — see `auth-platforms.md`. `frontend/prisma/seed.ts` also contains pricing data
for this table but does not run to completion, since it also seeds tables for Prisma
models absent from the current schema (`appConfig`, `equityHolding`, and others); it is not
the seed path this table's live rows come from.

This table is read by: the OAuth sign-in flow, which looks up the `FREE` row by `tier` to
assign new users their starting plan; `logSubscriptionPlanHistoryIfChanged()` (see
`subscription-plan-history.md`), which references a row's `id` when logging a plan change;
and the subscription checkout/upgrade flow (`POST /api/subscription/create`,
`POST /api/subscription/change-plan`), which reads a paid tier's `razorpayPlanId` to open a
Razorpay checkout and creates a `subscriptions` row against this plan's `id` — see
`../payments/subscription-reconciliation.md` for that flow's full design.

## Constraints & indexes

- **Primary key:** `id` (`uuid()`, generated by Prisma, not the database)
- **Unique constraint:** `tier` — enforces exactly one row per `Tier` value at the
  database level. Inserting a second `MONTHLY` row, for example, fails at the database
  layer, not just in application logic.
- No other indexes are defined.

---

## Data integrity caveats

Nothing in the schema enforces:
- That `offerPrice` is only set alongside a non-null `offerStartDate`/`offerEndDate` pair
  (or vice versa) — these three columns are independently nullable.
- That `offerEndDate` is after `offerStartDate`.
- That all four `Tier` enum values have a corresponding row, or that no extra rows
  exist beyond the four tiers (only the `@unique` on `tier` prevents *duplicates*, not a
  minimum/maximum row count). The `users.subscriptionPlanId` foreign key (see
  **Relationships**) prevents a *user* from pointing at a nonexistent plan row, but it
  doesn't require every tier to have a row — a missing tier just means no user could be
  assigned to it (there'd be no `id` to reference).
- That a paid tier (`MONTHLY`/`QUARTERLY`/`ANNUAL`) has a non-null `razorpayPlanId` — if one
  is missing, checkout for that tier fails at request time when the route tries to open a
  Razorpay subscription against a `NULL` plan ID, not at write time against this table.

These would need either a Postgres `CHECK` constraint (not expressible in Prisma's schema
language directly — would require a raw SQL migration) or application-level validation in
whatever write path is eventually built for managing pricing.

## Relationships

`users.subscriptionPlanId` is a foreign key into `subscription_plans.id`:

```prisma
model User {
  ...
  subscriptionPlanId String
  subscriptionPlan   SubscriptionPlan @relation(fields: [subscriptionPlanId], references: [id])
  ...
}
```

There is no `subscription` column on `User` — the tier name (`FREE`/`MONTHLY`/...) is read
via this relation (`user.subscriptionPlan.tier`), not stored on `User` directly.

The constraint is named `users_subscriptionPlanId_fkey` at the database level (verified
via `pg_constraint.confupdtype`/`confdeltype`). Practical implications:

- **Referential integrity is enforced by Postgres.** A `users.subscriptionPlanId` value
  must match an existing `subscription_plans.id` row — the database itself rejects a write
  otherwise. The four OAuth callback routes look up the `FREE` plan's `id` by `tier` at
  signup time (`prisma.subscriptionPlan.findUniqueOrThrow({ where: { tier: "FREE" } })`).
- **You cannot delete a `subscription_plans` row while any user still references its
  `id`** — `ON DELETE RESTRICT` blocks it.
- **Updating a `subscription_plans.id` cascades automatically** — `ON UPDATE CASCADE` is
  set (Prisma's implicit default for this kind of relation), so changing a row's `id`
  updates every `users.subscriptionPlanId` that pointed at it in the same statement.
- **The reverse relation** `SubscriptionPlan.users User[]` lets application code fetch
  `prisma.subscriptionPlan.findUnique({ where: { tier: 'MONTHLY' }, include: { users: true } })`
  to list every user on a given tier, though no code does this yet.
- Changing a `subscription_plans` row's `price`/`offerPrice` still has no automatic effect
  on any `User` row — the relation enforces which plan `id` values are valid, it doesn't
  copy pricing data onto `User` in any way.

`subscription_plans.id` is also referenced by `subscription_plan_history.subscriptionPlanId` —
see `subscription-plan-history.md`. The reverse relation
`SubscriptionPlan.subscriptionPlanHistory SubscriptionPlanHistory[]` lets application code list
every history row ever logged for a given tier.

**`subscriptions.subscriptionPlanId` → `subscription_plans.id`** (foreign key, reverse
direction): every Razorpay-backed `subscriptions` row is bound to the plan it was created
against — see `../payments/subscription-reconciliation.md`. The reverse relation
`SubscriptionPlan.subscriptions Subscription[]` lets application code list every
subscription ever created for a given tier. The `subscriptions` table itself is not yet
covered by a dedicated file in this `database/` folder — see its design in the payments
document above.
